The `vibrail` CLI does everything the dashboard does, from your terminal — run the platform, deploy a
project, tail logs, manage domains, and script it all in CI. It's the same binary you use to install and
run Vibrail itself.

<Callout title="Install it first">
This page assumes the `vibrail` command is already on your PATH. If not, see
[Installation](/docs/getting-started/installation) — the short version is `npm i -g @vibrail/cli` (or
`curl -fsSL https://raw.githubusercontent.com/aeolialiu2051/vibrail/main/scripts/install.sh | sh`).
</Callout>

Every command supports `--help`, so when in doubt:

```bash
vibrail --help              # top-level commands
vibrail deploy --help       # flags for one command
vibrail domain add --help   # flags for a subcommand
```

## Log in with a token

The CLI authenticates with a **Personal Access Token (PAT)** — a string that starts with `vibrail_pat_`.
You create one in the dashboard, then hand it to `vibrail login`.

<Steps>

<Step>

### Get a token

In the dashboard, open **Settings → Personal Access Tokens** and create one. Copy it — the secret is shown
only once. (You can also mint tokens from the CLI with [`vibrail token create`](/docs/cli/access).)

</Step>

<Step>

### Log in

Running `vibrail login` with no arguments opens that settings page and waits for you to paste the token.
For scripts and CI, pass it directly:

```bash
# Interactive — opens Settings and prompts for a paste
vibrail login

# Non-interactive — pass the token (great for CI)
vibrail login --token vibrail_pat_xxxxxxxxxxxx

# Point at a self-hosted instance instead of hosted Vibrail
vibrail login --token vibrail_pat_xxxxxxxxxxxx \
  --api-url https://your-host --dashboard-url https://your-host
```

The token is validated against the API and saved to `~/.vibrail/config.json`.

</Step>

</Steps>

| `vibrail login` flag | Purpose | Default |
|---|---|---|
| `--token <token>` | PAT (`vibrail_pat_…`) for non-interactive login. | prompt |
| `--api-url <url>` | API base URL to authenticate against. | `https://vibrail.warpgateapi.com` |
| `--dashboard-url <url>` | Dashboard base URL (opened for the paste flow). | `https://vibrail.warpgateapi.com` |
| `--context <name>` | Name of the [context](#connection-contexts) to store this login under. | `default` |

Set `HOST_DOMAIN` to change both hosted defaults without rebuilding the CLI. A bare hostname is interpreted
as HTTPS; `VIBRAIL_CLOUD_API_URL` and `VIBRAIL_CLOUD_DASHBOARD_URL` remain available as higher-priority,
per-endpoint overrides.

<Callout title="Signing out" type="info">
`vibrail logout` removes the stored token from the active context.
</Callout>

## Global flags

These work on every command.

| Flag | Purpose |
|---|---|
| `--json` | Machine-readable JSON output on stdout (data only — no spinners or prose). Ideal for piping into `jq` or consuming from scripts. |
| `--version` | Print the CLI version. |
| `--help` | Show help for the CLI or any command / subcommand. |

```bash
# Human-readable
vibrail project list

# Same data as JSON for scripting
vibrail project list --json | jq '.[].name'
```

## Connection contexts

A **context** is a named connection: an API endpoint, a dashboard endpoint, and the token to use with them.
They let one machine talk to more than one Vibrail instance — say a local install and a production
server — and switch between them without re-authenticating each time.

Contexts live in `~/.vibrail/config.json`. The one marked **current** is what every authenticated command
uses. `vibrail login` writes to the `default` context unless you pass `--context <name>`.

```bash
vibrail context            # list contexts; the active one is starred
vibrail context use prod   # switch the active context to "prod"
```

### Managing contexts

| Command | Purpose |
|---|---|
| `vibrail context` (alias `ctx`) | Show all contexts; the active row is starred. |
| `vibrail context list` (alias `ls`) | List configured contexts. |
| `vibrail context use <name>` | Switch the active context. |
| `vibrail context add <name>` | Create or update a context's endpoints/token. |
| `vibrail context rm <name>` (alias `remove`) | Remove a context (you can't remove the active one). |

Flags for `vibrail context add`:

| Flag | Purpose |
|---|---|
| `--api-url <url>` | API base URL. |
| `--dashboard-url <url>` | Dashboard base URL. |
| `--token <token>` | Personal access token to store. |
| `--use` | Switch to this context immediately after adding it. |

<Callout title="add vs. login" type="info">
`vibrail context add` only writes config — it doesn't check the token. Use `vibrail login` when you want
the token validated against the API before it's saved.
</Callout>

## All commands

Twenty-four commands, grouped the same way the reference pages are. Each heading links to the page that
covers those commands in full; run `vibrail <command> --help` for the flag list of any one.

### Running & updating — [reference](/docs/cli/run)

Operate Vibrail itself: the local server, the CLI, and the desktop app.

| Command | Purpose |
|---|---|
| `vibrail up` | Run Vibrail as a persistent service (starts on boot, auto-restarts). Ports are dynamic — a busy port is switched automatically. Add `--foreground` for a one-off attached run. |
| `vibrail stop` | Stop the service started by `vibrail up` (won't restart or return on reboot); also clears a stale database lock. |
| `vibrail reset-admin-password` | Reset the local admin login from this machine, without signing in (forgot-password recovery). |
| `vibrail update` | Update the CLI and bundled server to the latest release. |
| `vibrail install` | Download and install the Vibrail desktop app for this OS. |
| `vibrail install cache` | Manage the local download cache (list, verify, clean, path). |
| `vibrail open` | Open the Vibrail dashboard in your browser. |
| `vibrail status` | Show the local service (installed/running, resolved ports) and the active context's API health. |
| `vibrail doctor` | Diagnose the CLI setup (config, active context, runtime). |

### Access & the raw API — [reference](/docs/cli/access)

Who you are, which instance you're talking to, and an escape hatch to any route.

| Command | Purpose |
|---|---|
| `vibrail login` | Authenticate with a Personal Access Token. |
| `vibrail logout` | Remove the stored token from the active context. |
| `vibrail context` (alias `ctx`) | Manage connection contexts — see [above](#connection-contexts). |
| `vibrail token` | Manage personal access tokens (list, create, revoke). |
| `vibrail api` | Make an authenticated request to any Vibrail API route (like `gh api`). |

### Deploying — [reference](/docs/cli/deploy)

| Command | Purpose |
|---|---|
| `vibrail deploy` | Trigger a deployment for the current project. |
| `vibrail deployment` (alias `deployments`) | Manage deployments — list, inspect, redeploy, rollback. |
| `vibrail logs` | View or stream a deployment's logs. |

### Projects, services & domains — [reference](/docs/cli/projects)

| Command | Purpose |
|---|---|
| `vibrail init` | Link the current directory to a project (writes `.vibrail/project.json`). |
| `vibrail project` (alias `projects`) | Manage Vibrail projects. |
| `vibrail service` (alias `services`) | Manage the services in a compose stack (a multi-service project). |
| `vibrail domain` | Manage custom domains, DNS verification, and SSL certificates. |

### Self-host infrastructure — [reference](/docs/cli/self-host)

| Command | Purpose |
|---|---|
| `vibrail server` | Manage self-hosted SSH servers. |
| `vibrail system` | Instance settings, onboarding, migration, and data transfer. |
| `vibrail mail` | Self-hosted mail server (iRedMail) setup and admin. |
| `vibrail backup` | Manage backups — policies, runs, restores, and destinations. |
